After that, the full notification flow is live:

  - Admin rejects → student gets justification_rejected

    How Notifications Work                                                                                                                                         

    The two layers                                                                                                                                                                                                                                      
    Every notification does two things at once:

  1. Persists a row in the notifications table (inbox, permanent)
  2. Pushes a JSON message over WebSocket to any live connection for that user (real-time)

    This is done by the single function create_and_push() in notification_service.py.


    The WebSocket connection

    Both the Flutter app (students) and the web app (admins) connect the same way:

  ws://<host>/api/v1/ws/notifications?token=<access_jwt>

    - The server validates the JWT from the query string
    - Checks the user exists and is active in the DB
    - Registers the connection in a in-memory dict: { user_id → [WebSocket, ...] }
    - Keeps the socket open — client sends any message (e.g. "ping") to stay alive
    - On disconnect, the socket is removed from the dict

    One user can have multiple open connections (e.g. two browser tabs). All of them get the push.

  ---
  The two helper functions

  create_and_push(db, recipient_id, recipient_role, type, title, body, ...)
  - Saves one Notification row
  - Immediately pushes to that user's WebSocket if connected
  - Used for targeted notifications (one specific student or admin)

  notify_admins(db, type, title, body, ...)
  - Queries SELECT id FROM admins WHERE is_active = true
  - Calls create_and_push for each admin
  - Used when a student submits a justification (all admins need to know)

  ---
  Important limitation

  The ConnectionManager stores connections in memory on the running process. This means:

  - Works perfectly on a single-process deployment (Render with one worker)
  - If you ever scale to multiple workers or multiple instances, a user connected to worker A will not receive a push triggered on worker B — you would need a message broker (Redis Pub/Sub,
  etc.) to bridge them

Based on CompensationRequests.jsx (the empty list with "No pending requests" message, plus Approve/Reject buttons), here is the backend API you need:

1. POST /v1/compensation-requests — student asks to be present in a session
Body

{
  "session_id": "uuid",
  "student_matricule": "string",
  "reason": "string"
}
Response 201

{
  "id": "uuid",
  "status": "PENDING",
  "session_id": "uuid",
  "student_matricule": "string",
  "reason": "string",
  "created_at": "2026-06-02T10:00:00Z"
}
Student-side: only allowed for sessions where the student is not in the assigned group, or where they were marked absent.

2. GET /v1/compensation-requests — teacher fetches pending requests
Query params (all optional): status (PENDING/APPROVED/REJECTED), session_id, teacher_id (defaults to current teacher from JWT), page, page_size

Response 200

{
  "data": [
    {
      "id": "uuid",
      "studentName": "Doe John",
      "student_matricule": "string",
      "studentGroup": "G1",
      "targetGroup": "G2",
      "session_id": "uuid",
      "subject": "Algorithms",
      "room": "A101",
      "date": "2026-06-02",
      "time": "10:00 - 12:00",
      "reason": "I had a class swap",
      "status": "PENDING",
      "created_at": "2026-06-02T09:55:00Z"
    }
  ],
  "total": 0
}
Must only return requests for sessions owned by the calling teacher.

3. PATCH /v1/compensation-requests/{id}/approve — teacher approves
Body: none Response 200 — updated request, and the student is automatically added to the session roster (POST /v1/sessions/{id}/students is called internally, or a join row is created so the student shows up in GET /v1/sessions/{id}/attendance with is_present=true).

{
  "id": "uuid",
  "status": "APPROVED",
  "approved_at": "2026-06-02T10:05:00Z"
}
4. PATCH /v1/compensation-requests/{id}/reject — teacher rejects
Body (optional):

{ "reason": "string" }
Response 200

{
  "id": "uuid",
  "status": "REJECTED",
  "rejection_reason": "string",
  "rejected_at": "2026-06-02T10:05:00Z"
}
5. GET /v1/compensation-requests/me — student sees own requests (optional, for the student's dashboard)
Response 200 — same shape as endpoint #2, filtered to the calling student.

Minimal field set per request (matches CompensationRequests.jsx props)
Field	Source
id	request PK
studentName	student.full_name
studentGroup	student's own group
targetGroup	group of the session the student wants in
room	session.room.code / room.nom
date	session.date
time	session.start_time - session.end_time
subject	session.module.nom (optional, for UI)
status	PENDING / APPROVED / REJECTED
reason	student's note
created_at	timestamp
